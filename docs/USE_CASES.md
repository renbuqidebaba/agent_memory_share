# 从哪些场景开始使用 Agent Handoff？

> 评估日期：2026-10-04。下文是根据当前实现与公开一手资料提出的产品判断，尚未经过用户访谈或真实 agent 对照实验验证。

建议把**实现完成后的独立复验**作为第一条可演示工作流，把**排障卡住后的接手**作为第二条。
跨客户端交接是值得建立的后续能力，先用同一可信本机用户下的两个会话验证。

## 场景排序

| 优先级 | 场景与触发点 | 当前能力的直接价值 | 需要补齐或验收的环节 |
|---|---|---|---|
| 1 | 实现 agent 留下补丁，另一个会话负责复验 | 明确审哪份代码、按什么标准完成、谁已接手，以及退回原因 | 自动收集改动清单、结构化复验结果、交接与后续修复包的关联 |
| 2 | 排障已有失败现场，但当前会话停滞或结束 | 传递复现命令、失败日志与已排除假设，并发现日志/源码版本变化 | 环境信息与日志的选择性收集、脱敏、缺陷状态的更新方式 |
| 3 | 在同一台机器上切换编程客户端或模型 | 用工具无关的交接包保留任务事实和文件引用 | 至少两个真实客户端组合的端到端试验，以及清晰的任务发现入口 |
| 4 | 大型升级或重构分成多次会话完成 | 保存每一阶段的完成标准与剩余工作 | 交接链、阶段依赖、已接受任务的主动转交/撤销；当前不适合宣称无人值守编排 |
| 后续 | 跨机器团队、云端 CI 分发任务 | 将来可能复用交接格式 | 认证、访问控制、产物传输、环境重建；当前没有实现 |

这些优先级是产品假设，不是市场规模或需求强度评分。前两项优先，是因为它们能直接用现有工具完成一次交接，并用具体代码、测试与结论判断效果。
本文的操作基线是下方已试跑的 `create → claim → verify` 流程与分页演示；开发中的采集能力仍需完成相应验收后再纳入场景结论。

## 1. 实现 → 独立复验

**第一位用户**：一个开发者在本机使用两个 agent 会话，一个写代码，一个检查结果。

**触发点**：补丁已经可以审查，但开发者还不想把“发送方说测试通过”当作最终结论。
将本次交接的目标写为“复验这项改动”，完成标准是输出可检查的审查结论。这样 `complete` 表示复验任务结束，不表示原补丁一定没有缺陷。

从本仓库试用，在已激活项目虚拟环境、安装 `.[mcp]` 后：

```bash
# 发送方：先阅读模板，按本次改动调整目标、文件和完成标准。
agent-handoff create examples/handoffs/verification.json --workspace . --markdown verification-handoff.md

# 接收方：将 HANDOFF_ID 替换为创建返回值。
agent-handoff claim HANDOFF_ID --agent verification-agent
agent-handoff show HANDOFF_ID --markdown
agent-handoff verify HANDOFF_ID --workspace .
```

检查代码并决定接手后：

```bash
agent-handoff ack HANDOFF_ID --agent verification-agent --accept
# 运行适用的检查，把结论写入约定的位置；实际完成复验后：
agent-handoff complete HANDOFF_ID --agent verification-agent
```

若文件无法读取、版本不符或缺少完成标准，在接受前用
`agent-handoff ack HANDOFF_ID --agent verification-agent --reject --reason '具体原因'` 退回。
模板里的测试标为 `not_run`，不会自动执行。

**当前可做**：把复验当作有独立完成标准的任务来交接。
**当前限制**：完成命令还没有审查结果附件字段；需要人为约定结论文件。退回是终态，修订后要创建新包；没有自动修复循环。

**验证价值**：与“发一条普通审查请求”对比，总准备与接手时间是否下降？接收方能否检查正确版本、发现注入的缺陷、保留失败证据？不要只比较接手速度而忽略审查质量。

## 2. 排障 → 新 agent 接手

**第一位用户**：已经花时间复现和排除问题，需要换会话继续调查的开发者。

交接里应该写清：触发条件、预期与实际结果、最后一次失败输出、相关文件、已验证的假设、未验证的猜测。
日志可作为普通文件引用并计算摘要；源码和日志都需由接收方直接访问。

可以用现有分页任务获得一个真实失败现场：

```bash
python scripts/demo_handoff.py --output debug-handoff-demo --prepare-only
export HANDOFF_DB_PATH="$PWD/debug-handoff-demo/handoff.db"
agent-handoff list --task-id pagination-boundaries
```

新会话使用 `debug-handoff-demo/workspace` 作为工作区，以 `agent-b` 领取、核验后自行复现失败并补修。
发送方的失败输出位于工作区内的 `sender-tests.log`。这个准备脚本已有确定的修复答案，适合演示；正式效果实验应换成接收方未见过的真实任务。

**当前限制**：文件哈希不能证明环境相同。依赖版本、环境变量名、外部服务和数据条件需要手动写入交接说明；密钥与私人日志不应直接收集进包。

**验证价值**：复现问题之前需要追问多少次？是否重复已排除的调查？最终修复是否通过原始失败用例和回归测试？

## 3. 同机跨客户端交接

例如在一个客户端完成实现，把复验或后续排障交给另一个客户端；双方通过 CLI 或各自配置的 MCP 访问同一数据库和工作区。
当前应描述为“可配置的本机工作流”，不能把通用 MCP 接口直接等同于已验证的所有客户端兼容性。

首个试点只选一对客户端，记录版本、连接配置、各自能看到的文件、工具调用轨迹与失败情况。
现有 [MCP 指南](INTEGRATIONS.md) 提供 Codex 配置和协议级验证范围；第二个客户端仍需要独立验证。

若代码处在不同 worktree，先同步相同 HEAD 和产物；目前没有自动复制未提交改动或解决冲突的能力。
也不要把 claim 租约当作工作区锁：它约束的是交接包领取，不能阻止其他进程编辑文件。

## 为什么调整原来的“会话续接”定位？

- **已有原生会话恢复**：Claude Code 的官方工作流文档提供继续或恢复已有会话的方式。单纯“关掉后接着聊”有直接替代方案。因此这里更值得验证的是角色或工具切换时，任务事实和文件证据能否可靠交接。[官方说明](https://code.claude.com/docs/en/common-workflows#resume-previous-conversations)
- **进度文件本身就是有效基线**：Anthropic 的长任务实践使用进度记录、Git 历史与测试帮助后续会话接手。我们的结构化交接必须与这种普通方法比较，而不能预设自己更省时间。[工程实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- **完整编排已有专门框架**：LangGraph 提供持久执行和状态管理。当前项目适合先检验现有工具之间的交接价值；进程恢复、任务依赖调度与跨机器运行需要额外工程，现有包状态并不等于这些能力。[项目说明](https://github.com/langchain-ai/langgraph)

上述资料说明已有方案和工作流；“优先独立复验、再验证排障与跨客户端”是本项目的判断，并非这些来源给出的结论。

## 下一步应如何验收？

1. **选择性收集证据**：从显式选择的文件生成改动清单和交接草稿；测试输出由用户决定是否记录。比较生成时间与遗漏信息，避免自动扫描整个工作区。
2. **复验结果回写**：让接收方提交结构化结果，关联原始交接与后续修复，而不只是关闭一个状态。
3. **真实客户端试点**：围绕前两种任务验证一对客户端；成功后再添加会话结束钩子或快捷命令。

这三项是后续交付的验收目标，本文尚未验证这些完整工作流。用 [效果实验方案](EVALUATION.md) 的三组基线记录“准备 + 接手 + 完成”的总成本；同时记录正确性和失败案例，再决定扩展方向。
